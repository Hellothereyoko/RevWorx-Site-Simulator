## Run locally

Requirements: Node.js and Docker Compose.

1. Copy `.env.example` to `.env`.
2. Install dependencies with `npm ci`.
3. Start PostgreSQL with `docker compose up -d db`. The supplied schema and sample data are loaded automatically the first time the database volume is created.
4. Start the website with `npm run dev`.

The local database is persisted in the `postgres_data` Docker volume. The site connects as `rwz_site`, which can only append contact submissions through a database function. The future Java API connects as `rwz_api`, whose reads are restricted by PostgreSQL row-level security. Do not use the example passwords outside local development.

The Java API should call `get_login_user_by_email(email)` to retrieve the stored password hash, verify it in the API, and never return the hash to the browser. After authenticating, it must run customer queries in a transaction and set the trusted identity with a parameterized `SELECT set_config('app.user_id', ?, true)`. Owner and Admin roles can read all customer rows; Customer users can read only their own rows. Never derive this ID from an unauthenticated request parameter. The sample password hashes in `data.sql` are placeholders and must be replaced before enabling real logins.

On an existing database volume, apply `db/schema.sql` and `db/data.sql` using the local PostgreSQL administrator, not `DATABASE_URL`. The previous `contact_submissions` table, if present, is left intact; new submissions go to `Customer` and `Lead`.

## Test PostgreSQL and role access

The local PostgreSQL administrator is `postgres` / `local-admin-only`. This is a local development credential only. The site database user is `rwz_site` / `local-site-password`; the future Java API user is `rwz_api` / `local-api-password`. These users have different permissions and must not use the administrator account.

The seeded application Owner is `admin@example.com` (user ID `1`), but it has no usable password: `test-key-hash-owner` is a placeholder string in the `passwordHash` column, not a password or a valid hash. The seeded Customer is `jane@example.com` (user ID `2`). You can test PostgreSQL row visibility with these IDs before the Java login program exists:

1. Copy `.env.example` to `.env`, then run `docker compose up -d db`. On the first start, Compose creates the roles, tables, and sample rows.
2. In another terminal, run `docker compose exec -it db psql -U postgres -d revworxz` to open a local admin SQL session.
3. Check contact form submissions in the new schema:

   ```sql
   SELECT c.customerid, c.name, c.email, l.leadid, s.statusname, l.summary
   FROM customer AS c
   JOIN lead AS l USING (customerid)
   JOIN leadstatus AS s USING (statusid)
   ORDER BY l.leadid DESC;
   ```

4. To test Customer visibility, switch to the API role inside a transaction:

   ```sql
   BEGIN;
   SET LOCAL ROLE rwz_api_reader;
   SELECT set_config('app.user_id', '2', true);
   SELECT customerid, name, email FROM customer;
   COMMIT;
   ```

   This should show only Jane Doe. Repeat with user ID `1` to test Owner access; it should show both seeded customers. Without setting an ID, protected customer tables should return no rows. The site role can call `submit_contact_form` but cannot select customer rows.

5. To test the website end to end, run `npm run dev`, open `http://localhost:4321/contact`, and submit fake data. A successful submission redirects to `/contact?sent=1`; rerun the query above to see the new Customer and Inquiry Lead.

Use `docker compose down` to stop the local database without deleting its data. Compose’s initialization scripts only run for a new database volume; for an existing volume, apply the schema and seed scripts with the local database administrator. Do not use `docker compose down -v` unless you intend to delete the local database volume.

## Deploy

Build and run the site on a Node.js host with `npm run build` and `npm run start`. Apply `db/schema.sql` using the hosted database's administrator console; do not load `db/data.sql` in production because it contains sample customers and placeholder password hashes. Create a real Owner account with a hash generated by the Java API's password-hashing library before enabling login. Configure `DATABASE_URL` as a secret for the restricted `rwz_site` login. Configure the Java API with `API_DATABASE_URL` (a JDBC URL), `API_DB_USER`, and `API_DB_PASSWORD` for `rwz_api`. Never run either application with the database administrator credentials. Point the domain to the Node.js host and enable HTTPS there.

The contact form appends a row to `Customer` and a related `Lead` in the `Inquiry` status. The Shopify store and linked Google design form remain external.
